# xerlock 게임 개발자 블로그 랜딩 페이지 기획

- 작성일: 2026-09-08
- 상태: 구현을 위한 초안. 아래 수치와 문구는 제안이며 플레이 검증 후 조정한다.
- 대상: 홈페이지 `/`
- 콘셉트: **게임을 만들고, 과정을 기록하는 탐정의 사건 기록실**
- 게임 가제: **Xerlock: 런던의 추격전**

## 1. 기획 목표

현재 홈의 긴 자기소개와 최신 글 3개 구성을, 짧은 게임으로 개발자의 개성을 경험하고 글과 프로젝트를 탐색하는 랜딩 페이지로 확장한다.

방문자는 게임을 시작하지 않아도 누구의 사이트인지, 어떤 글과 프로젝트가 있는지 바로 알 수 있어야 한다. 게임은 선택적으로 즐기는 입구이며, 블로그 이용의 필수 단계가 아니다.

핵심 경험은 다음과 같다.

> 탐정이 되어 짧은 추격전을 즐긴다. → 범인을 놓치거나 추격을 완료한다. → 사건 파일로 제시된 블로그 글을 선택해 읽는다.

### 방향 선택

| 후보 | 장점 | 부담 | 결정 |
| --- | --- | --- | --- |
| 탐정 테마 러너 | 조작이 직관적이고 닉네임을 시각적으로 표현하기 좋음 | 장애물 간격과 조작감 조정 필요 | 첫 버전으로 채택 |
| 숨은 단서 찾기 | 추리 분위기가 강하고 글 주제와 연결하기 좋음 | 반복 방문을 위한 여러 현장 필요 | 후속 확장 후보 |
| 전투·생존 게임 | 사망 연출과 액션의 손맛이 명확함 | 조작과 제작 범위가 커짐 | 첫 버전에서 제외 |

## 2. 정체성과 표현

- 랜딩의 콘셉트 이름은 사용자가 제시한 `xerlock`을 사용한다.
- 현재 사이트의 제목·작성자 표기는 `Xerlocked`다. 콘셉트 도입만으로 사이트 전체 이름, 메타데이터, 계정 링크를 일괄 변경하지 않는다.
- 탐정의 코트와 모자, 안개, 굴뚝, 사건 파일로 분위기를 만든다. 캐릭터와 그림은 이 사이트를 위한 독자적인 디자인으로 제작한다.
- 메뉴와 주요 링크는 `블로그`, `프로젝트`, `검색`처럼 이해하기 쉬운 이름을 유지한다. 탐정 표현은 보조 제목과 게임 문구에 사용한다.
- 첫 버전의 실패는 잔혹한 사망 대신 **범인을 놓친 상황**으로 표현한다. 사용자가 구상한 ‘사망 후 랜덤 글 제안’의 흐름은 동일하게 유지한다.

### 첫 화면 문구 제안

> **게임을 만들고, 과정을 기록합니다.**  
> 게임 개발자 김근홍의 블로그입니다. 짧은 추격전에 참여하거나, 개발 기록을 바로 살펴보세요.

- 게임 제목: `Xerlock: 런던의 추격전`
- 시작 버튼: `추적 시작`
- 설명: `점프로 장애물을 피해 30초 동안 범인을 추적하세요.`
- 바로가기: `블로그 읽기`, `프로젝트 보기`

## 3. 홈 화면 구성

```text
┌───────────────────────────────────────────┐
│ 기존 헤더 · 홈 / 블로그 / 프로젝트 / 검색       │
├───────────────────────────────────────────┤
│ XERLOCK                                   │
│ 게임을 만들고, 과정을 기록합니다.                │
│ 짧은 소개 · 블로그 읽기 · 프로젝트 보기          │
│                                           │
│ ┌───────────────────────────────────────┐ │
│ │ 런던 지붕 · 탐정 · 안개 · 범인의 흔적       │ │
│ │            [추적 시작]                  │ │
│ └───────────────────────────────────────┘ │
├───────────────────────────────────────────┤
│ 짧은 개발자 소개 · 기존 소셜 링크 / 푸터         │
└───────────────────────────────────────────┘
```

- 게임은 별도의 전체 화면으로 열지 않고 홈 안의 고정된 영역에서 실행한다.
- 작은 화면에서는 모든 요소를 한 열로 배치한다. 게임의 가로세로 비율과 주변 여백을 조정해 가로 스크롤을 방지한다.
- 홈의 콘텐츠 폭 조정은 홈에 한정하고 공통 글 레이아웃의 폭을 변경하지 않는다.

## 4. 게임 규칙

### 기본 루프

1. 최초 방문에는 정지된 장면과 시작 버튼을 보여준다.
2. 시작을 선택하면 탐정이 자동으로 달리고 배경과 장애물이 이동한다.
3. 방문자는 점프 하나로 굴뚝과 상자를 피한다.
4. 장애물에 한 번 충돌하면 추적 실패로 종료한다.
5. 플레이 시간 30초를 버티면 추적 완료로 종료한다.
6. 결과 영역에서 글을 열거나 다시 플레이하거나 최신 글로 이동한다.

### 초기 조정값

| 항목 | 첫 구현 기준 |
| --- | --- |
| 한 판 길이 | 최대 30초, 일시정지 시간 제외 |
| 조작 | 단일 점프, 공중 추가 점프 없음 |
| 장애물 | 바닥 위 상자·굴뚝 2종, 구덩이는 제외 |
| 초반 안전 구간 | 처음 3초 동안 충돌 장애물 없음 |
| 난이도 | 10초·20초 지점에서 이동 속도를 소폭 높이되 최대 속도 제한 |
| 장애물 생성 | 점프 비행 시간과 착지 후 재도약 여유를 보장하는 패턴 중 선택 |
| 점수 | 추적 시간 표시. 순위표와 영구 기록 저장 없음 |
| 충돌 판정 | 그림보다 약간 작은 판정 영역으로 시각적으로 억울한 충돌 완화 |
| 재시작 | 시간·장애물·입력 상태를 초기화하고 안전 구간부터 시작 |

속도·중력·점프 높이는 별도 설정값으로 관리한다. 수치 확정보다 모바일과 데스크톱에서 같은 타이밍에 도약할 수 있는지 먼저 검증한다. 무작위 생성으로 피할 수 없는 장애물 조합이 나오지 않아야 한다.

### 입력과 일시정지

- 데스크톱: 게임 영역에 포커스가 있을 때 `Space` 또는 `↑`로 점프한다. 게임 장면 클릭도 같은 동작을 한다.
- 모바일: 게임 장면 터치 또는 별도의 `점프` 버튼을 사용한다. 한 번의 터치가 중복 입력되지 않게 한다.
- 누르고 있는 키의 반복 입력으로 자동 연속 점프하지 않는다.
- 게임 밖에서는 스페이스와 방향키의 기존 페이지 스크롤을 방해하지 않는다.
- `일시정지` 버튼과 게임에 포커스가 있을 때의 `Escape`로 정지한다.
- 탭이 숨겨지거나 게임 영역이 화면 밖으로 나가거나 키보드 포커스가 게임 밖으로 이동하면 일시정지한다.
- 돌아왔을 때 자동으로 달리지 않고 `추적 재개`를 선택해야 이어진다.

## 5. 결과 연출과 블로그 연결

### 실패 연출

충돌 → 달리기 정지 → 탐정의 모자가 날아감 → 모자가 사건 파일 위에 내려앉음 → 결과와 추천 글 표시.

전체 연출은 약 1초 이내를 목표로 한다. 첫 구현에서는 화면 정지와 짧은 전환부터 완성하고, 모자 연출은 후속으로 추가한다. 타자기 효과를 사용하더라도 버튼이나 글 제목의 표시를 지연하지 않는다.

> **추적 실패. 범인은 안개 속으로 사라졌다.**  
> 현장에 남겨진 기록을 발견했습니다. 읽어볼까요?
>
> 📁 {실제 블로그 글 제목}  
> {실제 글 요약}
>
> [기록 읽기] [다시 추적하기] [최신 글 보기]

### 성공 연출

> **추적 완료. 새로운 단서를 확보했습니다.**  
> 다음 사건으로 이어지는 기록을 발견했습니다.
>
> 📁 {실제 블로그 글 제목}  
> {실제 글 요약}
>
> [기록 읽기] [다시 추적하기] [최신 글 보기]

추리와 직접 관련 없는 개발 글도 있으므로, 해당 글이 게임의 정답이나 실제 공략이라고 주장하지 않는다.

### 추천 규칙

1. 빌드 단계에서 `blog` 컬렉션 중 `draft`가 참이 아닌 글을 후보로 준비한다.
2. 브라우저에는 추천에 필요한 `id`, `title`, `summary`, `href`만 전달한다. 본문 전체는 전달하지 않는다.
3. 한 판이 끝날 때 후보 중 한 개를 균등한 확률로 고른다. 결과 화면을 읽는 동안 선택은 바뀌지 않는다.
4. 후보가 두 개 이상이면 현재 페이지에서 직전에 추천한 글을 제외한다. 방문 이력이나 읽음 여부는 추적하지 않는다.
5. 후보가 한 개면 같은 글을 계속 추천한다. 후보가 없으면 추천 카드를 생략하고 `블로그 보기`와 재시작을 제공한다.
6. 주소는 기존 패턴인 `/blog/${entry.id}`로 만든다. 제목으로 slug를 새로 생성하지 않는다.
7. `기록 읽기`를 명시적으로 선택한 경우에만 같은 탭에서 글로 이동한다. 자동 이동, 카운트다운 이동, 새 창 강제 열기를 하지 않는다.
8. `최신 글 보기`는 블로그 탭으로 이동한다. 결과 영역은 게임 안에 표시해 다른 링크를 가리지 않는다.

이 추천 필터는 홈에서 초안을 추천하지 않기 위한 것이다. 현재 상세 경로와 RSS의 공개 정책까지 바꾸거나, `draft`만으로 사이트 전체 비공개가 보장된다고 가정하지 않는다.

## 6. 시각 디자인과 접근성

- 스타일: 낮은 해상도의 픽셀아트 또는 단순한 실루엣. 탐정·장애물·배경이 명확하게 구분되는 쪽을 우선한다.
- 배경: 런던 지붕과 가로등, 옅은 안개. 장식이 장애물의 경계를 가리지 않게 한다.
- 밝은 테마: 종이색 바탕과 짙은 잉크색. 어두운 테마: 밤색 배경과 밝은 글자, 제한적인 황동색 강조.
- UI 본문: 기존 Pretendard와 공통 스타일을 사용한다. 장식 글꼴은 필수 자산으로 추가하지 않는다.
- 소리: 첫 버전은 무음이다. 이후 추가하더라도 사용자가 켜는 방식으로 제공한다.
- 결과 제목과 버튼은 실제 HTML로 제공한다. 게임을 Canvas로 그리더라도 텍스트와 링크를 그림 안에만 넣지 않는다.
- 상태 변경은 접근성 알림으로 전달하되 매 프레임의 시간이나 점수는 읽어주지 않는다.
- 종료 시 결과 제목으로 포커스를 안내하고, 재시작 시 게임 입력 영역으로 돌려준다. 포커스를 가두지 않는다.
- 터치 버튼은 최소 44×44 CSS px의 영역과 명확한 포커스 표시를 제공한다.
- 동작 줄이기 설정에서는 장식 안개·시차 이동·모자·타자기 효과를 생략한다. 플레이에 필요한 이동만 유지하고 바로 글을 읽는 경로를 제공한다.
- JavaScript 비활성화나 게임 로드 실패 시에도 소개·글·프로젝트·메뉴를 이용할 수 있어야 한다.

## 7. 첫 버전 범위

### 포함

- 짧은 소개, 게임 영역, footer
- 탐정 캐릭터 1종, 배경 1종, 장애물 2종.
- 시작·점프·충돌·30초 완료·일시정지·재시작.
- 성공과 실패 시 랜덤 글 카드와 명시적인 이동 선택.
- 모바일 터치, 키보드, 밝은·어두운 테마, 동작 줄이기 대응.
- 후보 글이 없거나 하나뿐인 경우와 게임 오류의 대체 화면.

### 후속 확장

- 모자에서 사건 파일로 이어지는 세부 애니메이션.
- 수집 가능한 단서와 시각적 보상.
- 단서 종류와 블로그 태그를 연결한 추천.
- 여러 현장, 짧은 추리 사건, 계절별 배경.
- 선택적인 소리와 기기 내 최고 기록.

### 제외

- 로그인, 서버 저장, 전역 순위표, 멀티플레이.
- 게임 엔진 도입, 별도 UI 프레임워크 추가.
- 기존 글 URL·본문·공개 정책 변경.
- 게임을 완료해야 콘텐츠를 열 수 있는 잠금 기능.
- 분석 서비스나 방문 이력 수집 도입.

## 8. 기존 프로젝트에 맞춘 구현 설계

현재 홈은 `src/pages/index.astro`에서 공개 글을 조회해 최신 3개를 `ArrowCard`로 표시하고, `PageLayout.astro`를 사용한다. 이 구조를 재사용한다.

| 영역 | 구현 방향 |
| --- | --- |
| 홈 조합 | `src/pages/index.astro`에서 소개·게임· footer 배치 |
| 정적 UI | Astro 컴포넌트와 기존 `ArrowCard` 재사용 |
| 게임 UI | 상호작용이 필요한 부분만 SolidJS 컴포넌트로 분리 |
| 게임 로직 | 별도 TypeScript 모듈로 시간·점프·생성·충돌 관리 |
| 렌더링 | Canvas 2D를 우선 검토하고 결과·버튼·설명은 HTML로 제공 |
| 데이터 | Astro frontmatter에서 컬렉션 필터·정렬·추천용 데이터 가공 |
| 로딩 | 게임 부분에만 필요한 hydration 적용. `client:visible`을 우선 검토하고 실행 루프는 시작 후 가동 |
| 이미지 | 고정 게임 자산은 `public/` 하위 전용 폴더, 콘텐츠 이미지는 기존 처리 유지 |
| 문구 | 공통 사이트 문구는 `src/consts.ts`의 방식 유지, 게임 문구는 게임 영역에서 관리 |
| 메타데이터 | 기존 `PageLayout`·`BaseHead`와 `astro.config.mjs`의 사이트 주소 유지 |

새 파일 이름과 상세 폴더는 구현 시 주변 코드 패턴을 확인해 확정한다. 콘텐츠 스키마 변경이나 새 의존성은 첫 버전에 필요하지 않다.

### 실행 품질 기준

- 프레임 간 경과 시간을 기준으로 움직여 화면 주사율에 따라 속도가 달라지지 않게 한다.
- 일시정지 후 재개할 때 누적 시간으로 캐릭터나 장애물이 순간 이동하지 않게 한다.
- 크기가 바뀌면 좌표계를 안전하게 갱신하고, 필요하면 일시정지해 재개를 요청한다.
- 게임 로딩 전에도 동일한 영역을 확보해 화면이 갑자기 밀리지 않게 한다.
- 종료·정지·페이지 이탈 시 실행 루프와 이벤트를 정리한다. 재시작으로 루프가 중복 생성되지 않아야 한다.
- 초기 자산은 배경 1종과 작은 스프라이트 중심으로 제한하고 글과 메뉴의 표시를 지연하지 않는다.

## 9. 제작 순서와 완료 기준

### 1단계: 정적인 랜딩 구성

소개, 게임 대기 장면, footer를 배치한다. 모바일·데스크톱과 두 테마에서 읽기 흐름과 게임 영역의 크기를 확인한다.

완료 기준: 게임 실행 없이 모든 콘텐츠와 기존 메뉴에 접근할 수 있다.

### 2단계: 플레이 가능한 기본 게임

임시 도형으로 시작·점프·장애물·충돌·완료·일시정지를 구현한다. 그래픽 작업 전에 조작과 장애물 간격을 검증한다.

완료 기준: 키보드와 터치로 한 판을 끝낼 수 있고, 정지·재개·재시작이 일관되게 작동한다.

### 3단계: 글 추천 연결

실제 컬렉션 데이터로 결과 카드를 만들고 추천 예외 상황을 처리한다.

완료 기준: 결과에 실제 글이 표시되고, 읽기를 선택한 경우에만 올바른 기존 주소로 이동한다.

### 4단계: 테마와 마무리

탐정 그래픽, 짧은 결과 전환, 접근성, 오류 대체 화면을 적용한다.

완료 기준: 아래 항목과 `npm run build`를 통과한다. 구현 일정은 기본 게임의 조작감과 필요한 그래픽 작업량을 확인한 뒤 산정한다.

### 구현 검수 목록

- [ ] 첫 화면에서 게임 개발자의 블로그임을 알 수 있다.
- [ ] 시작을 선택하기 전에는 게임이 움직이지 않는다.
- [ ] 키보드와 터치 입력이 중복되거나 페이지 전체 조작을 차단하지 않는다.
- [ ] 모든 장애물 패턴을 정상적인 점프로 통과할 수 있다.
- [ ] 충돌과 시간 완료가 같은 프레임에 발생해도 결과가 한 번만 표시된다. 이때 충돌을 우선한다.
- [ ] 일시정지 중 추적 시간이 흐르지 않고 재개 시 위치가 튀지 않는다.
- [ ] 반복 재시작 후에도 속도와 입력 횟수가 달라지지 않는다.
- [ ] 추천 후보 0개·1개·여러 개에서 결과가 정상적이고 초안이 추천되지 않는다.
- [ ] 추천 제목·요약·링크가 일치하며 긴 제목도 버튼을 밀어내거나 가리지 않는다.
- [ ] 게임을 건너뛰거나 결과에서 최신 글로 바로 이동할 수 있다.
- [ ] JavaScript 없이도 소개·기존 링크·최신 글·프로젝트가 표시된다.
- [ ] 360px 모바일 폭과 데스크톱에서 가로 넘침이 없고 두 테마에서 장애물을 구분할 수 있다.
- [ ] 동작 줄이기, 키보드 포커스, 결과 상태 알림이 동작한다.
- [ ] 기존 검색·테마 전환·메뉴·글 카드 링크가 동작한다.
- [ ] `npm run build`의 타입·Astro 검사와 정적 빌드가 통과한다.

## 10. 기대하는 방문 경험

처음 온 방문자는 작은 추격전으로 개발자의 취향을 경험하고, 결과에서 관심 가는 글을 발견한다. 다시 온 방문자는 익숙한 메뉴나 최신 글로 바로 이동한다. 게임의 재미와 블로그의 읽기 편의성이 함께 유지되는 것을 완성 기준으로 삼는다.
